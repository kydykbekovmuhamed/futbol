# Футбол — платформа бронирования футбольных площадок

Полная концепция, сценарии, монетизация и этапы — в [football-app-roadmap.md](football-app-roadmap.md). Читать перед любой архитектурной правкой.

## Статус: Этапы 1, 2 и 3 реализованы

Этап 1 (MVP), Этап 2 (комьюнити/B2B) и Этап 3 (удержание) — все реализованы и покрыты тестами, см. хронологию ниже. Изначально в скоуп сессии входил только Этап 1 — Этапы 2/3 добавлены по последующему явному запросу пользователя, не проактивно.

### Этап 1 (MVP) — из раздела 6 roadmap:
- Бронирование по времени с показом всех свободных площадок на интервал
- Гибридное подтверждение брони (push + звонок/SMS одновременно, hold на задатке, таймер 5–10 мин, автовозврат при истечении)
- Продление игры с защитой слота от перехвата (слот держится на паузе, пока текущий игрок решает)
- Роль "администратор площадки" как системная сущность (не поле на User, а назначаемая роль per-площадка)
- Подписочная модель для площадок (базовый/продвинутый тир)

**Этап 2 (комьюнити, B2B-турниры, рейтинг) и Этап 3 (удержание, лента, статистика игроков) — вне скоупа.** Не проектировать под них заранее, не добавлять преждевременные абстракции — единственное исключение см. ниже.

## Архитектурное решение: роль администратора площадки

По явному требованию пользователя (см. roadmap 2.4 и раздел 8, вопрос 3) роль venue-admin спроектирована так, чтобы не переделывать её при запуске корпоративных турниров в Этапе 2:
- Роль не хранится как булево поле на модели пользователя (`is_admin`), а представлена отдельной сущностью-назначением (User ↔ Venue через промежуточную модель с полем роли), т.к. один и тот же человек может администрировать несколько площадок, а площадка — иметь нескольких админов.
- Эта модель осознанно не привязана к "владельцу" (физлицу) — что позволяет в будущем добавить туда же корпоративные роли (HR/офис-менеджер по турнирам) без миграции схемы.
- Кроме этого пункта — никакой другой архитектуры под Этап 2/3 заранее не закладывается.

## Решённые открытые вопросы (roadmap, раздел 8)

- **Вопрос 1** (UI: "админ отклонил" vs "админ не ответил"): клиенту — единый месседж ("слот недоступен, попробуйте другое время"); в БД статусы хранятся раздельно (`declined` / `expired`) для админ-аналитики и SLA по площадкам.
- **Вопрос 2** (платёжный hold в КР): провайдер ещё не выбран — заложена абстракция `HOLD_CAPTURE` / `CHARGE_AUTO_REFUND` поверх платежей (см. раздел "Стек и провайдеры"), бизнес-логика брони от стратегии не зависит.
- **Вопрос 3** (точка входа для корпоративных турниров): решено пользователем — в MVP не нужна, см. архитектурное решение выше.
- **Вопрос 4** (комьюнити-слой в MVP): решено пользователем — не в MVP, строго Этап 2.

## Стек и провайдеры (подтверждено пользователем)

- **Бэкенд**: Django 6.1 + DRF + PostgreSQL + Celery/Redis. Приложения — в `apps/` (accounts, venues, bookings, payments, notifications), конфиг — в `config/`.
- **Задаток**: FreedomPay (карточный эквайринг с hold, roadmap раздел 8 вопрос 2 — платёжный слой абстрагирован (`apps/payments`, поле `Payment.strategy`: `hold_capture` / `charge_auto_refund`), реальный код готов, credentials нет — см. раздел "Реальные провайдеры" ниже.
- **Уведомления**: Firebase Cloud Messaging (push) + Infobip (SMS/автозвонок). Реальный код готов, credentials нет — см. раздел "Реальные провайдеры" ниже; пока используется mock-реализация в `apps/notifications`.
- **Локальная разработка**: `docker-compose.yml` — Postgres на порту 15432 (5432/5433 заняты Windows-исключениями портов), Redis на 6379. Виртуальное окружение — `venv/`, зависимости — `requirements.txt`.

## Прогресс по шагам MVP

1. ✅ Модели БД (accounts, venues, bookings, payments, notifications) — защита от двойного бронирования через `ExclusionConstraint` в Postgres, проверено вживую.
2. ✅ Бронирование: `GET /api/venues/available/?start=&end=&<фильтры>` (поиск по интервалу, roadmap 2.1) + `POST /api/bookings/create/` (создание брони с резервированием задатка через `apps.payments.providers`). Проверено сквозным HTTP-тестом: поиск → бронь → слот пропадает из выдачи → повторная бронь того же интервала возвращает 409.
   - Логин: `POST /api/auth/token/` (DRF authtoken, поле `username` = телефон). Полноценной регистрации/OTP пока нет — вне рамок этих 4 шагов, пользователи создаются через Django admin/shell.
   - Задаток — 30% от стоимости (`BOOKING_DEPOSIT_PERCENT` в settings), стоимость = `price_per_hour × часы`.
3. ✅ Подтверждение (гибридное): при создании брони — push+SMS+звонок всем активным админам площадки (`apps/notifications`, пока mock-провайдер, логирует вместо реальной отправки). Celery планирует напоминание за 2 мин до дедлайна и автоотмену по таймауту (`apply_async(countdown=...)`, не periodic beat — таймер персональный на каждую бронь).
   - `POST /api/bookings/<id>/confirm/` и `.../decline/` (админ площадки, поле `channel`: push/sms/call — какой канал реально использован, для аналитики). Подтверждение списывает задаток, отклонение/автоотмена — освобождает/возвращает.
   - Гонки (админ жмёт кнопку ровно когда срабатывает таймер) разрешаются через `select_for_update()` на Booking и Payment — кто первый берёт блокировку строки, тот и выигрывает; проигравший видит уже изменённый статус и получает `BookingAlreadyResolved` (409) либо тихий no-op для таймера.
   - Проверено сквозным тестом: подтверждение → списание, отклонение → возврат, "срабатывание таймера" (вызван напрямую, как это сделает Celery) → возврат, повторный вызов любого из трёх — безопасный no-op без повторного списания/возврата. Задачи реально долетают до Redis (проверено `redis-cli llen celery`).
   - **Нужен запущенный Celery-воркер, чтобы таймеры реально срабатывали**: `celery -A config worker -l info` (beat не нужен — расписание per-booking через countdown).
4. ✅ Продление игры (roadmap 2.3): за `BOOKING_EXTENSION_PROMPT_BEFORE_MINUTES` (15 мин) до конца подтверждённого слота Celery создаёт бронь-продление на следующий час в новом статусе `EXTENSION_PENDING` (`apps/bookings/models.py`) — она такая же "занимающая слот" для `ExclusionConstraint`, что и `CONFIRMED`/`PENDING_CONFIRMATION`, поэтому другой клиент физически не может перехватить время, пока текущий игрок решает.
   - В отличие от исходной брони, продление подтверждает **сам клиент**, без администратора: `POST /api/bookings/<id>/extension/confirm/` и `.../extension/decline/` (только владелец брони, иначе 403). Не ответил до конца текущего слота — та же Celery-автоотмена (`expire_booking`), что и для обычной брони, слот освобождается.
   - Явный отказ клиента ("не хочу продлевать") — статус `CANCELLED` (используем существующее значение, ранее не задействованное), не `DECLINED` (тот зарезервирован за отказом администратора, см. вопрос 1).
   - Продление можно продлевать повторно (цепочкой) — после подтверждения продления снова планируется предложение продлить ещё раз, той же логикой.
   - `expire_booking()` обобщён на оба "ожидающих" статуса (`AWAITING_DECISION_STATUSES`); клиенту не шлём "слот недоступен" при непродлении — это не ошибка, а нормальный исход.
   - Проверено сквозным тестом (сценарии A–D): продление блокирует слот от перехвата (`IntegrityError` при попытке параллельной брони), повторный вызов планировщика — идемпотентный no-op, подтверждение/явный отказ/таймаут — все три исхода корректно списывают/возвращают задаток, чужой пользователь не может подтвердить/отклонить чужое продление (403). Плюс отдельный HTTP-прогон через `curl` на реальном dev-сервере.

**Все 4 шага MVP реализованы и проверены сквозными тестами.**

## Регистрация/вход по телефону (OTP)

Добавлено сверх исходных 4 шагов: `POST /api/auth/otp/request/` {phone} → SMS-код (пока mock, логируется вместо реальной отправки) → `POST /api/auth/otp/verify/` {phone, code} → аккаунт создаётся автоматически при первом успешном коде (`set_unusable_password()` — пароля нет вообще, вход только по коду), возвращает DRF-токен. Регистрация и вход не различаются — один и тот же флоу.
- Cooldown на повторный запрос кода — `OTP_REQUEST_COOLDOWN_SECONDS` (60 сек), лимит попыток ввода — `OTP_MAX_ATTEMPTS` (5), TTL кода — `OTP_TTL_MINUTES` (5).
- Старый `POST /api/auth/token/` (телефон+пароль) не убран — им пользуются аккаунты с паролем, созданные через admin/shell (например тестовые фикстуры и, в будущем, возможно staff-доступ).
- Попутно рефакторинг: интерфейс `NotificationProvider` (`apps/notifications/providers.py`) переведён с `user` на `phone: str` — SMS/push реально адресуются номеру телефона, а не User, и это должно было работать ещё до создания аккаунта (иначе OTP на регистрации некому было бы слать).
- Проверено сквозным HTTP-тестом: новый номер → код → cooldown при повторном запросе (429) → неверный код (400) → верный код создаёт юзера и токен → токен реально авторизует → повторное использование того же кода отклонено (400). Старый вход по паролю продолжает работать.

## Автотесты

Всё, что раньше проверялось вручную через curl/скрипты, формализовано в `apps/accounts/tests.py` и `apps/bookings/tests.py` (35 тестов, Django `TestCase`/`APITestCase`, без моков Celery/Redis — на TestCase `transaction.on_commit()` не срабатывает, поэтому диспетч уведомлений и планирование задач в тестах просто не выполняются, тестируется только то, что действительно меняет состояние БД; для запуска нужен только Postgres, Redis не требуется).

Запуск: `python manage.py test apps.accounts.tests apps.bookings.tests` (именно так, полным путём к модулю — короткие лейблы `accounts`/`bookings` или `apps.accounts` не резолвятся корректно тест-раннером в этой версии Django, разбирался специально). Первый прогон против Docker-Postgres на Windows может занимать 2–3 минуты (создание/удаление тестовой БД), сами тесты быстрые.

Покрыто: создание брони + все варианты отказа (прошлое время, конец раньше начала, двойное/пересекающееся бронирование, освобождение слота после отклонения), подтверждение/отклонение/автоотмена админом с проверкой списания/возврата задатка и гонки "таймер сработал после ручного подтверждения", весь флоу продления (блокировка слота, идемпотентность повторного предложения, подтверждение/явный отказ/таймаут владельцем, отказ чужому пользователю), OTP-регистрация/вход (cooldown, неверный/просроченный/повторно использованный код, лимit попыток) — как на уровне сервисов, так и через реальные HTTP-запросы (`APIClient`).

## Этап 2 (в разработке)

Решения по открытым вопросам roadmap (раздел 4, 4.1), подтверждённые пользователем:
- Корпоративные турниры — раздел внутри основного приложения, без отдельной точки входа для HR (можно добавить лендинг позже).
- Самообслуживание турнира (4.1) — взнос за участие и оплата газона раздельными платежами (проще технически, площадке не важно происхождение брони).

### Прогресс
1. ✅ **Команды и статистика** (`apps/teams`): `Team` (рейтинг — очковая система 3/1/0 за победу/ничью/поражение, **не ELO** — ELO явно отнесён roadmap'ом в банк идей на будущее, раздел 7, не в Этап 2), `TeamMembership` (капитан/игрок), `Match` (результат между двумя командами, опционально привязан к `Booking`).
   - `POST /api/teams/` (создатель автоматически капитан), `GET /api/teams/`, `GET /api/teams/<id>/`, `GET /api/teams/<id>/members/`, `POST /api/teams/<id>/join/`, `.../leave/`
   - `POST /api/teams/matches/` (создать матч — только участник одной из команд), `POST /api/teams/matches/<id>/report-result/` (внести счёт — обновляет рейтинг обеих команд атомарно, `select_for_update`)
   - **Сознательное упрощение MVP**: результат матча фиксирует один участник любой из двух команд без подтверждения второй стороной и без разбора споров — это не то, как должно быть в идеале, а компромисс по объёму работ. Дуэльное подтверждение результата — кандидат на доработку, если станет реальной проблемой.
   - Покрыто 14 тестами (`apps/teams/tests.py`) — создание/дубли имён, вступление/выход, права на создание матча и ввод результата, начисление очков (победа/ничья), запрет повторного ввода результата.
2. ✅ **Поиск соперника / поиск игрока в состав** (`apps/matchmaking`): `OpponentRequest` (команда с подтверждённой бронью ищет, с кем сыграть — привязана к `Booking`, `OneToOne`) и `PlayerRequest`+`PlayerApplication` (команде не хватает игроков на конкретную игру, желающие откликаются, капитан принимает/отклоняет).
   - `POST /api/matchmaking/opponent-requests/` (только владелец подтверждённой брони и участник команды), `.../match/` (другая команда откликается, не может ответить сама себе), `.../cancel/`
   - `POST /api/matchmaking/player-requests/` (участник команды), `.../apply/` (не-участник, нельзя откликнуться дважды), `.../applications/` (список откликов), `POST /api/matchmaking/applications/<id>/accept|decline/` — при наборе нужного числа игроков (`spots_needed`) заявка закрывается автоматически.
   - Оба приложения (`teams`, `matchmaking`) ссылаются на `bookings.Booking`/`teams.Team` через строковые FK (`"bookings.Booking"`) — циклического импорта на уровне Python нет, только в `matchmaking/serializers.py` есть прямой `from apps.bookings.models import Booking` (для `PrimaryKeyRelatedField`, где строковая ссылка не работает) — это безопасно, т.к. `apps.bookings` не импортирует `apps.matchmaking`/`apps.teams` в обратную сторону.
   - Покрыто 13 тестами: подтверждённость/владение брони, членство в команде, запрет отклика на свою же заявку, запрет повторного отклика/двойного матчинга, автозакрытие при наборе состава, права на решение по заявкам.
3. ✅ **Корпоративные турниры** (`apps/tournaments`): `Tournament` (взнос, min/max команд, дедлайн регистрации, `sponsor_name` — "Турнир при поддержке [бренд]", roadmap 4.1), `TournamentRegistration` (взнос холдируется сразу при регистрации той же hold/capture/release-схемой, что и задаток за площадку), `TournamentMatch` (пара команд + раунд + обёртка над `teams.Match`, чтобы не дублировать логику результата/рейтинга).
   - **Платёжный рефакторинг**: `Payment` был жёстко привязан к `Booking` (OneToOne, обязательное поле) — обобщил под `CheckConstraint` "ровно одна цель" (`booking` ИЛИ `tournament_registration`, оба nullable), а `PaymentProvider.hold()` теперь принимает `reference: str` вместо `booking` — провайдер в принципе не должен знать о конкретных моделях домена. Все вызовы в `apps/bookings/services.py` обновлены (`reference=f"booking-{id}"`).
   - `POST /api/tournaments/` (создание, планирует Celery-таймер на `registration_deadline`), `.../registrations/` (регистрация команды — только участник команды), `.../registrations/<id>/cancel/`, `.../registrations/<id>/disqualify/` (неявка — организатор, взнос **не** возвращается), `.../matches/` (только организатор турнира создаёт пары), `.../matches/<id>/report-result/` (участник любой из играющих команд, как в обычных матчах), `.../standings/` (турнirная таблица — считается на лету по счёту матчей этого турнира, 3/1/0 очка).
   - **Автозакрытие регистрации по дедлайну** (`close_registration`, Celery): meньше `min_teams` зарегистрировалось → турнир `CANCELLED`, все взносы возвращены; иначе → `REGISTRATION_CLOSED`, все взносы списаны. Отвечает на "вопросы механики регистрации" из roadmap 4.1.
   - **Сознательное упрощение MVP**: сетка турнира не генерируется автоматически (без алгоритма плей-офф с авто-продвижением победителей) — организатор создаёт пары матчей вручную, раунд за раундом. Полноценный bracket-генератор — следующий шаг поверх этой структуры, если понадобится, а не то, что нужно было делать ради Этапа 2.
   - Покрыто 16 тестами: резерв/списание/возврат взноса, лимит команд, дедлайн в прошлом, автозакрытие (недобор/добор, идемпотентность), права на создание матчей и ввод результата (только организатор/только участник команды), дисквалификация не возвращает взнос, сквозной HTTP-прогон турнира от создания до турнирной таблицы.
4. ✅ **Монетизация — комиссия с брони и с турнирного взноса** (roadmap, раздел 3 и 4.1): `Venue.commission_percent` (по умолчанию `DEFAULT_VENUE_COMMISSION_PERCENT=10`, настраивается per-площадка) и `Tournament.organizer_commission_percent` (по умолчанию `DEFAULT_TOURNAMENT_ORGANIZER_COMMISSION_PERCENT=12`, per-турнир). `Payment.commission_amount` считается и сохраняется **только** в момент реального списания (`CAPTURED`) — со снятого резерва/возврата/неудачного списания комиссии не бывает, это чисто учётное поле для отчётности, без фактического payout площадкам/организаторам (реальных денег провайдер ещё не двигает).

## Догон 2: тот же разрыв закрыт для турнирных взносов

По запросу "отлично работай" (снова без уточнения) — тем же паттерном, что и для брони выше, закрыл идентичный пробел для `apps.tournaments`: раньше при асинхронной неудаче оплаты турнирного взноса вебхук `.../result/` только помечал платёж `FAILED` и оставлял регистрацию в статусе `REGISTERED` — команда занимала бы место в турнире навсегда, хотя деньги не списались.

- Новая функция `cancel_registration_after_payment_failure(registration_id)` (`apps/tournaments/services.py`, рядом с `_settle_entry_payment`) — идемпотентный no-op, если регистрации нет или она уже не `REGISTERED` (например, отменена самим игроком); иначе переводит в `CANCELLED` и освобождает место.
- Проактивно, ещё до того, как баг успел повториться: добавил в `_settle_entry_payment` тот же guard `if payment.status != PaymentStatus.HELD: return`, что и в `apps.bookings._settle_payment` — иначе вызов из вебхука на уже-`FAILED` платеже попытался бы второй раз снять резерв через `cancel.php`.

## Фронтенд: реализация дизайн-макета (`apps/frontend`)

По запросу "реализуй этот макет" (макет — 6-экранный дизайн-канвас "Футбол — дизайн приложения", сделанный ранее через Claude Design skill) поднят реальный клиентский SPA поверх существующего REST API. Просто перезапустил процесс вручную после того, как все файлы существовали — воспроизводимо для любого будущего Django-приложения, добавленного на лету в этом проекте (**если после `python manage.py runserver` шаблон/статика 404-ят сразу после создания — не отлаживать код, просто перезапустить сервер**).

Добавлены 4 чистые демо-площадки (Арена Ак-Ордо, Спорт-Сити Восток-5, Байтик Арена, Динамо Стадион) — те же названия, что в самом макете, для правдоподобного демо.
- **Проверено**: JS-синтаксис (`node --check`), `python manage.py check`, и весь цикл через реальные HTTP-запросы (curl/`requests`, в обход `manage.py shell`-пайпа — см. ниже) — OTP request/verify → поиск с фильтром по площадкам (включая кириллический `district`) → создание брони (поля ответа 1:1 совпадают с тем, что ждёт `app.js`) → подтверждение админом → `GET /api/bookings/` отдаёт статус `confirmed`, как и ожидает поллинг. **Визуально в браузере не проверял** — нет инструмента браузерной автоматизации в этой сессии; страница открыта пользователю по `http://127.0.0.1:8001/`, реальную проверку кликами должен сделать пользователь.
- **Повторно наступил на грабли кириллицы на Windows** (см. [[windows-cyrillic-cli-encoding]]) — на этот раз не через `python -c`, а через `python manage.py shell < script.py` (стдин-пайп в интерактивную оболочку Django): те же симптомы (побитые байты при выводе в терминал). Показавшееся "повреждение данных" при первой попытке засеять демо-площадки оказалось ЛОЖНОЙ тревогой — реальные байты в Postgres были целые, мойибейк был только в отображении Git Bash терминала; но при перезаписи всё равно пересоздал их через прямой запуск `.py`-файла (`python script.py`, не пайп), это и есть единственный надёжный способ на этой машине. Заодно нашёл, что `curl --data-urlencode` в этом Git Bash тоже не всегда надёжно передаёт кириллицу/спецсимволы (`+` в ISO-датах превращался в пробел без него) — для отладки с не-ASCII данными надёжнее писать `.py`-скрипт с `requests`, чем городить curl-флаги.

**Полный тест-сьют бэкенда не менялся этим шагом** — фронтенд не покрыт автотестами (ванильный JS без тестового раннера в этом заходе), 145 тестов Django остаются актуальными.

### Догон фронтенда: правки по живым багам от пользователя + экран ExtendGame

Пользователь тестировал фронтенд вживую в браузере (то, что я сам проверить не мог — нет инструмента браузерной автоматизации) и нашёл реальные баги, плюс попросил доработать UX и реализовать следующий экран макета:

- **CSRF-баг при входе** — `POST /api/auth/otp/request/` падал с "CSRF Failed: CSRF token missing". Причина: в этом же браузере раньше логинились в Django admin, браузер по умолчанию слал cookie сессии на запросы к API, DRF `SessionAuthentication` при успешной сессионной аутентификации требует CSRF-токен (это специально, защита от CSRF через залогиненную сессию — `APIView`-уровневый `csrf_exempt` тут не помогает, он про другое). Фикс на фронтенде: `fetch(..., {credentials:"omit"})` во всех запросах `app.js` — наше приложение всегда работает через `Token`-авторизацию, cookie ему не нужны вообще.
- **OTP-ввод: 6 отдельных клеточек с фокус-джаглингом заменены на одно текстовое поле** (`maxlength=6`, `inputmode=numeric`) — с 6 полями при перерендере после ошибки фокус сбрасывался на первую клетку с уже введёнными (неверными) цифрами, backspace вёл себя нелогично. Одно поле проще и надёжнее; при ошибке код теперь ещё и очищается автоматически (`state.otpCode=""`), не нужно вручную стирать.
- **Скрытие нативных scrollbar + edge-fade** для горизонтальных лент (часы, фильтры) — `scrollbar-width:none`+`::-webkit-scrollbar{display:none}` плюс полупрозрачная тень 36px по краям (`.fade-wrap`, `.hscroll`), видимость тени переключается JS-функцией `bindScrollFade()` по факту scrollLeft/scrollWidth — тень с нужной стороны исчезает у истинного края контента, а не просто "всегда видна". Заодно уменьшил пилюли часов (компактнее, больше влезает на экран) — это было ДО следующего пункта, который вообще убрал этот ряд из основного потока.
- **Замена двух рядов (дни отдельно + часы отдельным горизонтальным скроллом) на единый компонент**: свёрнутая строка "Сегодня, 18:00–19:00" с chevron-down → тап открывает bottom sheet (`.sheet-backdrop`/`.sheet-panel`, slide-up анимация) с лентой дней (пилюли, как раньше) и сеткой часов `grid-template-columns:repeat(4,1fr)` вместо горизонтального скролла. Выбор дня оставляет шторку открытой (даёт уточнить час), выбор часа — применяет и закрывает.
- **Ручной ввод даты**: в шторку добавлен `<input type="date">` (стилизован под пилюлю, `color-scheme:dark` + инвертированная иконка календаря) — раньше можно было выбрать только один из 4 быстрых вариантов (сегодня/+1/+2/+3). Потребовало рефакторинга модели даты в `app.js`: `state.dateOffset` (0–3 для быстрых пилюль) дополнен `state.customDateParts` + сентинел `dateOffset===-1`; везде, где раньше был прямой `bishkekDateParts(state.dateOffset)`, теперь `selectedDateParts()` — она разруливает, что активно.
- **Фильтр "Район"**: было текстовое поле, стилизованное под `<select>` (со стрелочкой), что вводило в заблуждение — на самом деле не список, а точный/подстрочный текстовый ввод. У Бишкека всего 4 района — по запросу пользователя заменил на обычный `<select>` с фиксированным списком (`DISTRICTS` в `app.js`, те же названия, что в демо-площадках), убрал старый `.filter-district-input`.
- **Нечитаемые опции у `<select>`**: раскрытый список опций браузер рисует своим нативным (белым) попапом, а `color` для текста наследовался от `.select-pill{color:var(--text)}` (почти белый) — светлый текст на белом фоне. Добавлено явное `.select-pill option{color:#211d16;background:#fff}`.
- **Контрастность пилюль фильтров** — фон/бордер были почти не видны на тёмном фоне страницы (`var(--surface2)` + едва заметный `var(--line)`), заменил на `rgba(255,255,255,0.1)` фон / `rgba(255,255,255,0.22)` бордер + светлее chevron — той же полупрозрачной логике, что уже использовалась для `.time-select-row`.
- **Экран ExtendGame** (`ExtendGame.dc.html`, roadmap 2.3) реализован как глобальный оверлей, который может появиться поверх ЛЮБОГО экрана (не только поиска) — соответствует смыслу продления: клиент может быть где угодно в приложении, когда наступает время решать. Механика: `startExtensionWatch()` — фоновый опрос `GET /api/bookings/` раз в 20 сек (запускается после логина/на буте, если уже есть токен; останавливается при логауте) ищет бронь в статусе `extension_pending`; при находке — `state.extensionOffer` + рендер поверх текущего вида (`.ext-backdrop`/`.ext-sheet`, тот же slide-up паттерн, что и у шторки времени, z-index выше). Кнопки "Продлить"/"Нет, спасибо" → `POST /api/bookings/<id>/extension/confirm|decline/`. Countdown и прогресс-бар считаются от `confirmation_deadline`/`created_at` брони-продления той же формулой, что и кольцо в `BookingConfirm` — у продления единственный дедлайн (`confirmation_deadline == end_time` исходной брони, см. `offer_extension()` в `apps/bookings/services.py`), отдельного "второго таймера" нет, хотя в макете выглядит как будто их два (countdown+progress bar) — на самом деле это одно и то же значение, просто два визуальных представления.
- **Проверено сквозным API-тестом** (не в браузере — по тем же причинам, что и раньше): создание брони → подтверждение → `offer_extension()` (то, что в проде вызвал бы Celery) → оба исхода, `.../extension/confirm/` и `.../extension/decline/`, оба возвращают 200 и корректный статус; поля ответа (`price`, `confirmation_deadline`, `created_at`) точно совпадают с тем, что рендерит `renderExtensionOffer()`.

**Экраны `TeamProfile`/`Feed` из макета всё ещё не реализованы** — следующий шаг тем же паттерном, если попросят.

### Найден и исправлен реальный краш: "Команда" вечно грузится после Команда→Турниры→Команда

Пользователь сообщил: первый заход на "Команда" — идеально, но после захода на "Турниры" и возврата обратно на "Команда" экран вечно висит на спиннере, и это не чинится повторным нажатием — только полный рефреш страницы. Воспроизвести и понять причину без браузерной автоматизации (её нет в этой сессии) удалось через точную симуляцию: скопировал тело `app.js` в Node-скрипт с минимальными стабами `document`/`localStorage`/`fetch` (стаб `getElementById` реально проверяет, есть ли `id="..."` в последнем отрендеренном HTML — как настоящий браузер, а не слепо возвращает фейковый узел), прогнал точную последовательность `goToNav("team") → goToNav("cup") → goToNav("team")` через реальные `loadMyTeam()`/`goToNav()` — и поймал `TypeError: Cannot read properties of null (reading 'addEventListener')`.

**Корневая причина**: `bind()` для экрана "Команда" решал, привязывать ли кнопки `team-leave-btn`/`team-challenge-btn`/`team-invite-btn`, только по `if (state.myTeam)` — но `renderTeam()` сам решает, что рисовать, по `state.teamLoading` В ПЕРВУЮ ОЧЕРЕДЬ (спиннер, если `teamLoading`, и только потом — по `!state.myTeam`/полный профиль). При повторном заходе на "Команда" `loadMyTeam()` ставит `teamLoading=true` и рендерит спиннер — а `state.myTeam` при этом ещё остаётся от прошлого визита (не сбрасывается), поэтому `bind()` ошибочно решает, что отрисован полный профиль, и пытается привязать кнопку, которой физически нет в DOM (спиннер-версия `teamHeader()` её не рисует) → `null.addEventListener` → необработанное исключение → `render()` обрывается ДО того, как реальный `fetch` вообще успевает уйти на сервер → экран навсегда остаётся на спиннере предыдущего успешного рендера, а повторный клик просто наступает на те же грабли.

**Фикс**: `if (state.myTeam)` → проверка на существование самого DOM-элемента (`var leaveBtn = document.getElementById("team-leave-btn"); if (leaveBtn) {...}`) — тот же защитный паттерн, что уже использовался в `tournament-detail` bind (проверять то, что реально отрендерилось, а не пересчитывать условие рендера заново и рисковать, что они разъедутся). Общий урок для этого файла: там, где `bind()` привязывает кнопки, которые рендерятся условно, — проверять существование элемента, а не дублировать условие рендера отдельной веткой `if`.

Подтверждено той же Node-симуляцией — после фикса `goToNav("team") → goToNav("cup") → goToNav("team")` доходит до сервера обоими разами и корректно завершает загрузку.

**Теперь у бронирования, турнирного взноса и подписки команды — одинаковая, полная redirect-flow обработка.** Единственное, что реально осталось нетронутым в этой теме — сама живая проверка против настоящей песочницы FreedomPay (нет credentials) и Infobip DTMF-вебхук (см. разделы выше) — то, что физически нельзя закрыть без внешнего доступа.

### 2. Автотесты для фронтенда (`apps/frontend/tests/`) — впервые за всю сессию

Фронтенд был реализован полностью, но без единого автотеста ("ванильный JS, без тестового раннера" — так и было записано весь этот раздел сессии). Формализовал технику отладки, которой поймал баг "Команда" (см. выше, [[node_harness_for_browser_js_debugging]]), в постоянный регрессионный тест — без добавления в проект Jest/jsdom/любых новых зависимостей:

- `apps/frontend/tests/dom_stub.js` — минимальный стаб `document`/`localStorage`/`navigator`/`window`: `getElementById` реально проверяет `id="..."` в последнем отрендеренном HTML (как настоящий браузер), а не слепо возвращает фейковый узел — иначе тест не поймал бы именно ту категорию бага, ради которой его писали.
- `apps/frontend/tests/fixtures.js` — реалистичные формы ответов API, проверенные вживую через curl в ходе разработки (не выдуманные на месте).
- `apps/frontend/tests/run.js` — читает РЕАЛЬНЫЙ `app.js` заново при каждом запуске (не копию/снэпшот), вырезает секцию `// ---- boot` и подставляет вместо нее `driver_body.js` — значит тест всегда бьёт по актуальному коду, а не устаревшей версии.
- `apps/frontend/tests/driver_body.js` — 18 сценариев одной сквозной сессией (не изолированные unit-тесты) — именно так был найден реальный баг: через ПОСЛЕДОВАТЕЛЬНОСТЬ переходов, а не изолированный рендер одного экрана. Отдельно выделен сценарий `REPRO: team -> tournaments -> team` — точное воспроизведение найденного бага, чтобы он гарантированно не вернулся незамеченным.
- Запуск: `node apps/frontend/tests/run.js` (ничего дополнительно ставить не надо, чистый Node). Возвращает ненулевой exit code при падении — можно использовать как gate.
- **Проверено, что тест реально что-то ловит, а не просто зелёный**: временно откатил фикс "Команда" → 4 из 18 сценариев упали ровно там же, где нашли баг вживую → вернул фикс → снова 18/18. Не просто "написал тест и он прошёл" — подтверждено, что он ловит регресс.
- `_generated_harness.js` (промежуточный файл, склеенный из app.js + driver) — в `.gitignore`, это артефакт запуска, не исходник.

**Полный тест-сьют бэкенда: 148 тестов (145 + 3 новых для redirect-flow подписки), все проходят вместе** (`apps.accounts apps.bookings apps.teams apps.matchmaking apps.tournaments apps.payments apps.notifications apps.community`). Фронтенд теперь тоже имеет автотесты — 20 сценариев, `node apps/frontend/tests/run.js`.

### 3. Экран подписки команды / расширенной статистики — ещё один давно готовый, но не показанный бэкенд

Раз уж закрывал пробелы — `apps.community.TeamSubscription`/`TeamExtendedStatsView` были полностью готовы и протестированы с Этапа 3, но у них никогда не было фронтенд-экрана вообще (в отличие от "Мои брони" и "Турниры" выше, тут даже отдельного напоминания в CLAUDE.md не было — просто выпало из виду). Добавил секцию на TeamProfile:

- `checkTeamSubscription(teamId)` — отдельного "проверить подписку" эндпойнта в бэкенде нет, сам `GET /community/teams/<id>/extended-stats/` и есть проверка: `200` с данными = активна, `402` = нет. Вызывается вместе с загрузкой команды (`loadMyTeam()`), не блокирует основной рендер профиля — своя мини-загрузка внутри секции.
- Нет подписки → карточка "Расширенная статистика" + кнопка "Оформить" → `POST /community/teams/<id>/subscribe/` (тот же паттерн `payment_redirect_url`, что и у брони/турнира/только что переписанной подписки — см. пункт 1 выше).
- Есть подписка → сворачиваемая карточка: win rate, лучшая серия побед, помесячная разбивка (`monthly_breakdown`) — раскрывается по клику (`teamStatsExpanded`), не занимает место на экране по умолчанию.
- Намеренно НЕ показываю цену подписки в UI (500 сом/30 дней по `settings.TEAM_SUBSCRIPTION_PRICE`/`DURATION_DAYS`) — ни один GET-эндпойнт эту цифру не отдаёт, дублировать константу из бэкенда в JS вручную не стал (риск разъехаться при следующем изменении цены в settings).
- **Проверено дважды**: 20/20 в `apps/frontend/tests/` (включая честную симуляцию 402 в фейковом `fetch`, иначе тест не поймал бы `undefined.monthly_breakdown.map`, если бы кто-то по ошибке считал пустой ответ за "подписка есть") и сквозным вызовом реального API (`curl`): 402 до оформления → `POST subscribe/` → 200 с реальными данными после. Заодно теперь "Барс FC" в деве с активной подпиской — при открытии в браузере сразу видно обе ветки UI, а не только пустую заглушку.

**Все три пробела из этого захода закрыты.** Реально нетронутым остаётся только то, что физически нельзя сделать без внешнего доступа: живая проверка FreedomPay/Firebase/Infobip против их песочниц и уточнение формата Infobip DTMF-вебхука.
